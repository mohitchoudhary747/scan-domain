Cookie Initiator Repro Page

Live reproduction of the malformed “Initiator Call Stack” bug for cookie scanning.

Round 1 (below, in the “static inline” group) tested whether plain inline <script> blocks produce an empty-URL initiator. They didn't — the scanner correctly attributed them to this page's own URL. Round 2 tests sourceless execution (eval(), new Function(), stringified setTimeout, and a dynamically created & appended <script> element). On tiaa.org, the actual mechanism is confirmed: GTM (container GTM-WKK389C) fires Adobe's AppMeasurement.js — complete with its channelManager/eVar41 plugin that literally writes cmgvo — as a Custom HTML tag, i.e. one dynamically-created <script> whose .text is that entire multi-function library, not a one-liner. dynscript_cookie below now mirrors that shape (several nested function calls deep in a multi-KB blob) instead of a trivial single statement. Round 3 tests a different candidate: Securiti's own consent SDK gates Adobe/GTM firing, so the real cookie write may happen inside an async Promise callback several microtask hops away from any synchronous script — a stack-capture scenario very different from a flat script body. tracker.js is loaded as an external file so its cookies get a normal, correctly-attributed initiator to compare against.
